# FNE 通用提权包格式规范 · `fne-rootpkg` v1

> 本文件是 **App 内 `FrpImporter` 与 `frp_tool.py` 的共同契约**，两者校验规则必须一致。
> 格式由本项目自定义；扩展名 **`.frp`**，物理载体是标准 ZIP（deflate）。

## 1. 设计原则

1. **只能整包导入**。App 不提供「单独替换 e」「单独替换 sh」的入口；导入单元是且仅是 `.frp` 单文件。
2. **原子校验**：先解到临时目录 → 全项校验 → 通过后才原子替换 `active_pkg/`；任何一项失败，不写入任何业务文件。
3. **只做 5.4 系**。`kernel_series` 必须是 `"5.4"`，`kernel_releases` 每一条必须以 `5.4.` 开头。
4. **首次释放之后不再校验**。导入时一次性校验，运行时不再做 md5/尺寸比对（避免历史「自愈覆盖把 e 写坏」的问题）。

## 2. 目录结构

```
<包名>.frp                      # ZIP
├── manifest.json               # 必需，UTF-8 JSON，包元数据 + 文件清单 + 执行契约
├── payload/                    # 必需，10 项运行时物料，文件名固定
│   ├── e
│   ├── fne_local.sh
│   ├── chain_hook.sh
│   ├── fne_syms.txt            # 明文（不压缩）
│   ├── kernelsu.ko
│   ├── ksud
│   ├── magiskpolicy
│   ├── load_ko
│   ├── kmsg_dumper
│   └── ksu_rules
├── offsets/
│   └── offsets.json            # 必需，5.4 系偏移需求表
└── README.md                   # 可选，包内自述
```

**路径安全**：所有条目不得为绝对路径、不得含 `..`、不得含反斜杠或盘符前缀（防 zip-slip）。
**条目唯一**：ZIP 内不得出现同名条目（v22 强制）。同名条目在不同 ZIP 实现里 `getEntry()` 与遍历顺序不一致，会造成「校验读 A、导入落盘 B」的歧义。

## 3. `manifest.json` 顶层字段

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `format` | string | ✔ | 固定 `fne-rootpkg` |
| `format_version` | int | ✔ | 固定 `1` |
| `kernel_series` | string | ✔ | 固定 `5.4` |
| `package` | object | ✔ | 包身份，见 §4 |
| `execution` | object | ✔ | 执行契约，见 §5 |
| `files` | array | ✔ | 物料清单，见 §6 |
| `offsets_ref` | string | ✔ | 固定 `offsets/offsets.json` |

> **v22 类型约束**：`format_version`、`files[].size`、`execution.e_size`、`assertions.*` 里的数值
> 必须是 **JSON 整数**，不能写成 `"1"` / `"221104"` 这类字符串。PC 端与 App 端都用严格整数判定，
> 避免同一个包两端结论相反。

## 4. `package`

| 字段 | 说明 |
|---|---|
| `id` | 包唯一 ID，小写字母/数字/连字符 |
| `name` | 展示名 |
| `device` | 机型，如 `FNE-AN00` |
| `android` | 系统版本描述 |
| `kernel_releases[]` | **本包实际放行**的内核 `uname -r` 精确串（非「e 支持的全部内核」） |
| `ko_vermagic` | 必须与 `payload/kernelsu.ko` 内 `vermagic=` 逐字一致 |
| `built` | 构建日期 |
| `notes` | 自由文本，建议写明门控锁定范围 |

## 5. `execution`

| 字段 | 说明 |
|---|---|
| `workdir` | **必须** `/data/local/tmp/ksu_fne`。e 二进制内部硬编码此路径，改动即失效 |
| `e_path` | **必须** `/data/local/tmp/ksu_fne/e` |
| `entry_script` | **固定 `fne_local.sh`**（v23 起写死）。释放/搬运/执行命令都用这个名字，不允许包自述改名 |
| `e_size` | `e` 的字节数（JSON 整数）；**该十进制串必须真的出现在 `fne_local.sh` 文本里**，否则视为「换了 e 没换 sh」而拒绝 |
| `hardcoded_paths[]` | 列出所有硬编码路径，供人工复核 |
| `assertions` | 记录脚本/ko/chain 内的硬编码断言（尺寸、vermagic、内核指纹、符号表行数），逐项与物料实值比对。**v23 起由 `build` 从实际物料重算并覆盖模板**，不允许沿用旧模板值 |
| `env` | 运行时注入的环境变量，**必须含 `DM_PAGE_OFFSET`**（5.4 系 `__va()` 绝对映射，取 `0xffffff8000000000`） |

## 6. `files[]` 每项

| 字段 | 说明 |
|---|---|
| `path` | ZIP 内路径，**固定 `payload/<dest>`** |
| `dest` | 释放到 `workdir` 下的目标文件名，**由 role 唯一决定且必须互不相同** |
| `role` | 见下表，10 个角色各恰好 1 项，**不得出现白名单外的 role** |
| `size` | 字节数（JSON 整数），导入时逐项比对 |
| `sha256` | 导入时逐项比对 |
| `mode` | 由 role 唯一决定的 `0755` / `0644`，四位八进制字符串 |
| `desc` | 说明 |

**v22 强绑定**：`files[]` 恰好 10 项；对每个 role，`dest` / `mode` / `path` 必须与下表逐字一致，
且 `dest`、`path` 在整个清单里唯一。这样「交换两个 role 的 dest」「两个 role 写同一个 dest 相互覆盖」
「两个 role 指向同一个 path」「清单里夹带第 11 项」都会被拒绝。

### 必需角色（10 个，一个都不能少）

| role | payload 文件 | mode | 说明 |
|---|---|---|---|
| `exploit` | `e` | 0755 | aarch64 ELF，`EM_AARCH64=0xB7` |
| `entry_script` | `fne_local.sh` | 0755 | 有 `#!`，通过 `sh -n` |
| `chain_hook` | `chain_hook.sh` | 0755 | 有 `#!`，通过 `sh -n` |
| `kallsyms` | `fne_syms.txt` | 0644 | 行数与 `assertions.kallsyms_lines` 精确一致；未声明时 ≥ 200000 |
| `kernelsu_ko` | `kernelsu.ko` | 0644 | vermagic 与 `package.ko_vermagic` 一致 |
| `ksud` | `ksud` | 0755 | |
| `magiskpolicy` | `magiskpolicy` | 0755 | |
| `load_ko` | `load_ko` | 0755 | |
| `kmsg_dumper` | `kmsg_dumper` | 0755 | |
| `ksu_rules` | `ksu_rules` | 0644 | |

> **x 位提醒**：除 `e` 和两个 `.sh` 外，`ksud / magiskpolicy / load_ko / kmsg_dumper` 也必须有 x 位。
> 真机上漏一个，e 的 `[ -x chain_hook.sh ]` 或后续链就会走 `root-no-ksu` 分支。

## 7. `offsets/offsets.json`

| 字段 | 说明 |
|---|---|
| `series` | `5.4` |
| `scope` | 明确写出不覆盖 5.10 / 5.15 / 6.x 及原因 |
| `addressing` | 偏移的编址方式（`kallsyms VA - kimage_text_base`） |
| `struct_macro_5_4` | `STRUCT_OFFSETS_5_4` 的 31 项结构体布局 |
| `field_dictionary[]` | 75 项字段字典：name / category / meaning / how_to_get / required（**仅作说明，不参与判卷**） |
| `runtime_contract` | `P0_PAGE_OFFSET`、`GL_MEMSTART` 等运行时量 |
| `kernels[]` | 5.4 系内核条目，每条含 `uname_r` / `cluster` / `status` / `offsets{}` |
| `warning` | 偏移错误会静默写坏内核内存的告警 |

**校验（v23，基准内置化）**：

- `offsets_ref` **固定** `offsets/offsets.json`，不认包内指定路径。
- `kernels` 非空，全部 `uname_r` 以 `5.4.` 开头且**不重复**。
- `package.kernel_releases` 里的**每个**内核都必须在 `kernels` 中有条目（**全覆盖**，不是 v22 的「至少一个」）。
- 每条内核的 `offsets{}` 必须覆盖**代码内置 `OFFSET_FIELDS` 的 75 个字段**，且每个值必须是**非负、无前导 `+`、无下划线、长度受限**的数字：非负 JSON 整数（**v25 起 ≤ `Long.MAX` = `0x7FFFFFFFFFFFFFFF`**）、`0[xX][0-9a-fA-F]{1,16}` 十六进制串、或 `[0-9]{1,20}` 十进制串，可带 `UuLl` 后缀。`0b` / `0o` / `1_000` / `+0x10` / `-0x10` / 400 位巨数一律拒绝（**v24 起两端用同一套正则**，见 §11；此前 PC 用 `int(s,0)`、App 用 `BigInteger`，语法不一致导致同一包 PC 放行、App 拒绝）。裸 `NaN` / `Infinity` 字面量 v25 起在词法层被拒（Python `json.loads` 认、org.json 不认）。
- **`offsets/offsets.json` 与 `manifest.json` 一样过 `jsonGuard` / `json_guard` 词法预检**（v25）：BOM / 非法 UTF-8 / 体积 ≤ `MAX_OFFSETS_SIZE`(4 MB) / 嵌套 ≤ 64 / 同一对象内无重复键 / 无非标准裸字面量。App 端必须用**严格 UTF-8 解码后的文本**构造 `JSONObject`，不能用 `new String(bytes, "UTF-8")`（后者会把非法字节替换成 U+FFFD 后照常解析，第五轮 G1）。此前 offsets 是「第二份独立 JSON」却零预检，导致「PC 拒 / App 放行」。（**v26 补充**：上述预检已升级为严格 RFC 8259 词法状态机，覆盖字符串内转义/控制字符与字符串外数字/裸标识符/结构位置，见 §8.3。）

> **为什么字段清单要内置**：v22 把「必备字段清单」从包内 `field_dictionary[]` 读取，攻击者把字典砍到 1 项、或把 74 项标成 `required:false`，就能让校验器「自己出题自己判卷」全部放行（第三轮 A1/A2/A3）。v23 起字典只是**说明文档**，判卷用代码里写死的 75 项常量（PC `OFFSET_FIELDS` / App `Frp.OFFSET_FIELDS` 逐字一致）。同理 `MIN_KALLSYMS_LINES=200000`、`OFFSETS_REF`、`ENTRY_SCRIPT` 全部内置。

## 8. 交叉校验（为什么必须整包）

导入时除逐文件校验外，还要校验**物料之间的配套关系**：

| 检查 | 原因 |
|---|---|
| `e` 是 aarch64 ELF（**e_machine 两字节 == 0x00B7**） | 装错架构直接跑不起来；v23 修掉「只查低字节会放行 0x1B7」的跨端差异 |
| `execution.e_size` == `e` 实际尺寸，且该尺寸十进制串出现在 `fne_local.sh` | 换 e 不改 sh 的自检会 FATAL 退出；v22 补齐静态绑定 |
| `kernelsu.ko` 的 vermagic == `package.ko_vermagic`，且该串同时出现在两个 `.sh` | 不一致会在 insmod 前 abort 或 panic；v22 补齐静态绑定 |
| 两个 `.sh` 都含 `workdir` 全路径 | 改目录即失效；v22 补齐静态绑定 |
| `assertions.*` 与 e 尺寸 / ko vermagic / 符号表行数逐项比对 | 断言原本只是备注，v22 起参与校验；**v23 起由 build 从物料重算** |
| `fne_syms.txt` 行数 >= 内置下限 200000，且与 `assertions.kallsyms_lines` 一致 | v22 允许包自述 `kallsyms_lines=1` 就放行 1 行符号表（第三轮 A4）；v23 加硬下限 |
| 两个 `.sh` 有 shebang 且 **`sh -n` 通过（两端都真跑）** | v22 只有 PC 端跑，App 端放行坏脚本（第三轮 B3）。两端都用系统 `sh -n` 从 stdin 读脚本，零临时文件、零执行；**不用静态括号/关键字配平**，因为官方 sh 里 `case`/注释/跨行引号本就不配平，启发式会误伤合法脚本 |
| 每个 role **恰好 1 项**；包内**无清单外条目** | 防重复声明与夹带文件；v21 补齐 |
| `files[]` 恰好 10 项；role ↔ dest ↔ mode ↔ path 全绑定且唯一 | 防物料错位 / 相互覆盖 / 夹带未知 role；v22 补齐 |
| ZIP 内**无重复条目名** | 防「校验读 A、落盘 B」；v22 补齐 |
| 偏移表 75 内置字段全覆盖 + 值可解析、releases 全覆盖、`offsets_ref` 固定 | 防包自述规则（第三轮 A1/A2/A5/A6）；v23 补齐 |
| **manifest 词法预检**：BOM / 非法 UTF-8 / 长度 ≤ 64 KB / 嵌套 ≤ 64 / 同一对象内无重复键 | 重复键与 BOM 造成「两端结论相反」，5000 层嵌套让 App 抛 `StackOverflowError` 崩溃（第四轮 E2/E3/E4）；v24 补齐 |
| **ZIP CRC 两端都校验** | Java `ZipFile.getInputStream` 不校验 CRC，PC 抛 `BadZipFile` 崩溃而 App 放行（E1）；v24 补齐 |
| **目录条目纳入「无未声明条目」** | `/` 结尾条目被两端当目录跳过，可夹带任意内容（E6）；v24 补齐 |
| **资源上限**：包 ≤ 64 MB / 条目 ≤ 64 / 单条目 ≤ 16 MB / 总解压 ≤ 48 MB / 脚本 ≤ 2 MB | 24 MB `README.md` 与 40 MB 符号表两端放行，受限堆下 App OOM（E8/F4）；v24 补齐，且读取时边读边卡上限防伪造 size |
| **偏移值数字字面量两端对齐** | `0b101` / `0o17` / `1_000` / `+0x10` / `-0x10` 全部「PC 放行 / App 拒绝」（E5）；v24 补齐 |
| **两份 JSON 都过词法预检** | `offsets/offsets.json` 是包内第二份独立 JSON，此前零预检：非法 UTF-8 / BOM → PC 拒 App 放，两个 `kernels` 键 → 两端都放行（第五轮 G1/G2/G3）；v25 补齐 |
| **偏移值 JSON 整数上界对齐 Long.MAX** | PC 无限精度 int 放行 2^64-1，org.json 把它解析成 Double 而 `parseNumOk` 拒绝（第五轮 G6）；v25 把 PC 上界收到 `0x7FFFFFFFFFFFFFFF` |
| **容器层全量 CRC + 真实字节数** | 白名单 `README.md` 从不被 `read()`：CRC 改坏 / ZIP 头声明 size 伪造（真实 6MB 声明 100）→ PC 拒 App 放，且 App `install()` 真把 6MB 写进激活包（第五轮 H1/H6）；v25 逐条目流式算真实 CRC 与真实字节数、与声明比对 |
| **两份 JSON 过严格 RFC 8259 词法状态机**（v26） | 抽查式预检把裁决权交给两个方言差异极大的解析器：`+1`/`01`/`0x1`/`nan`/`inf`/`True`/非法转义/裸控制字符 → 13 例 PC 拒 App 放（第六轮 J/K/M 组） |
| **数字字面量严格匹配 + 尾部粘连检查**（v26） | `files[].size: +221104`、`kallsyms_lines: 0x32C2F` 被 App 当成自洽整数 → 整包放行，`install` 还把方言 manifest 落盘（第六轮 P03/P05） |
| **字段类型契约 + 自由文本单行约束**（v26） | `package.id` 为数字/对象两端一致放行；`id` 塞换行 + 伪造 `[OK]` 行可注入界面日志（第六轮 L01/L02/P06） |

## 8.1 容器层与资源上限（v24）

两端（`frp_tool.py` / `Frp.java`）使用**同一组内置常量**，逐字一致：

| 常量 | 值 | 官方示范包实测 |
|---|---|---|
| `MAX_PKG_SIZE` | 64 MB | 压缩后 8.8 MB |
| `MAX_ENTRIES` | 64 | 13 条 |
| `MAX_ENTRY_SIZE` | 16 MB | 最大 11,095,147 B（`fne_syms.txt`） |
| `MAX_TOTAL_SIZE` | 48 MB | 25,024,800 B |
| `MAX_MANIFEST_SIZE` | 64 KB | 4,716 B |
| `MAX_JSON_DEPTH` | 64 | 正常 3～4 层 |
| `MAX_SCRIPT_SIZE` | 2 MB | 最大 11,517 B（`chain_hook.sh`） |

`Frp.read()` 在解压时**边读边累计**，超过 `MAX_ENTRY_SIZE` 立即放弃，不信 ZIP 头里声明的
`size`（可能是伪造的）。`jsonGuard()` / `json_guard()`（v25 由 `manifestGuard` 泛化）在把字节交给
JSON 解析器之前做确定性词法扫描，两端各一份、逻辑逐行对齐，并返回严格 UTF-8 解码文本供构造；
`verifyZip` 的 `catch` 兜 `Throwable`，兜住 `StackOverflowError` 等 Error。

## 8.2 校验盲区与容器层（v25）

第五轮发现：前四轮把 `manifest.json` 与 `payload/*` 守严了，但包内还有两处**从未被任何规则覆盖**
的成员 —— 第二份独立 JSON `offsets/offsets.json`、白名单纯文档 `README.md`。

**通用 JSON 预检**（`jsonGuard(byte[] raw, int maxSize)` / `json_guard(raw, max_size)`）：

| 项 | `manifest.json` | `offsets/offsets.json` |
|---|---|---|
| 体积上限 | `MAX_MANIFEST_SIZE` = 64 KB | `MAX_OFFSETS_SIZE` = 4 MB（v25 新增） |
| BOM / 非法 UTF-8 / 重复键 / 深度 ≤ 64 / 裸 NaN·Infinity | ✔ v24 | ✔ **v25 补齐** |
| 用严格解码文本构造 JSON 对象 | ✔ v25 | ✔ **v25 补齐** |

**容器层全量校验**（App `Frp.verifyContainer(ZipFile, Result)` / PC `real_entry_len()`）：

前四轮的 CRC 只在 `read()` 里、且只对「本次会读取的条目」做；`README.md` 从不被读取，
`ZipEntry.getSize()` 又是可伪造的**声明值**。v25 对**每个条目**独立流式扫描，算真实 CRC、
累计真实解压字节数，与 `getCrc()` / `getSize()` 逐条比对，任一条不符即整体拒绝；边读边卡
16 MB 上限，不把整条目读进内存。

| 攻击面 | v24 及以前 | v25 |
|---|---|---|
| `README.md` 中央目录 CRC 改坏 | PC `testzip` 全量拒 / App 不查 → 放行 | 全量条目 CRC → 两端都拒 |
| `README` 真实 6MB、声明 `size=100` | PC 按声明读到 CRC 不符拒 / App 信声明值放行 | 真实字节数 ≠ 声明 → 两端都拒 |
| `install` 落盘按 deflate 流写满 6MB | 落盘循环无真实字节上限 | 边写边累计，超 16MB 抛异常回滚 |
| 同时把 CRC 重算成「声明那点字节」的 CRC | PC `testzip` 自洽通过 | PC `real_entry_len` 读真实字节数与声明比对 → 拒 |

> `README.md` 的**内容解码**刻意不做：它是纯文档，不参与运行/搬运/解析，只做 CRC、真实字节数、
> 体积校验。因此塞非法 UTF-8 字节两端一致放行（第五轮 H2）—— 这是设计选择，不是遗漏。

**数值边界**：两端偏移值的 JSON 裸整数统一上界 `INT_MAX = 0x7FFFFFFFFFFFFFFF`（Long.MAX）。
字符串形式的 `0x` 十六进制（官方 825 个值）不受此限。

## 8.3 JSON 严格词法裁决（v26）

第六轮发现：前五轮的词法预检只是**抽查**（BOM / UTF-8 / 体积 / 深度 / 重复键 /
大写 `NaN`+`Infinity`），「什么算合法 JSON」的最终裁决权仍落在两个方言差异极大的
解析器手里：

| 字面量 | PC `json.loads` | App `org.json` |
|---|---|---|
| `+1` / `01` / `0x1` | 拒绝 | **解析成 `Integer:1`** |
| `1.` / `.5` | 拒绝 | **解析成 `Double`** |
| `nan` / `inf` / `None` / `1e` | 拒绝 | **当字符串** |
| `True` / `False` | 拒绝 | **当 `Boolean`** |
| 非法转义 `\q` | 拒绝 | 吞掉反斜杠 |
| `\u+072` | 拒绝 | `Integer.parseInt` 认前导 `+` |
| 字符串内裸 `0x01` | 拒绝 | 接受 |

结果：13 例「PC 拒 / App 放」，其中 `files[].size: +221104` 与
`assertions.kallsyms_lines: 0x32C2F`（=207919）让 App 认为**字段与实际物料自洽**而整包放行，
`install()` 甚至把带 `+221104` 的方言 manifest 落盘成激活包。

**v26 规则**：`jsonGuard(byte[], int)` / `json_guard(raw, max_size)` 在把文本交给解析器之前，
用确定性 6 态状态机 `VAL / VAL_REQ / KEY / KEY_REQ / COLON / DELIM` 统一裁决：

| 层 | 规则 |
|---|---|
| 字符串内 | 转义白名单 `"` `\` `/` `b f n r t u`；`\u` 后严格 4 位 `[0-9a-fA-F]`；拒绝裸控制字符 `< 0x20` |
| 字符串外·数字 | 必须匹配 `-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?`，尾部不得粘连非结构字符 |
| 字符串外·裸标识符 | 只允许精确小写 `true` / `false` / `null` |
| 字符串外·结构 | `{ } [ ] : ,` 位置由状态机判定，尾随逗号 / 双冒号 / 括号错配一律拒；其它字符一律拒 |
| 深度 / 重复键 | 沿用 v24/v25：≤ 64 层、同一对象内键唯一 |

> **词法层成为唯一裁决者**：org.json 的方言根本进不了解析器，而不是在 App 端
> 补一堆特判去模拟 Python 的严格性。两端实现逐条对齐，由
> `simulate/bugcheck_v6.py` 的 29 个包每包单独 JVM 交叉实测。

同时补**字段类型契约**：App `str()` 由 `optString()`（会把数字 / 对象 `toString` 成文本）
改为只取真正的 JSON 字符串；两端对 `package.id` / `name` / `ko_vermagic` 要求
单行纯文本、无控制字符、≤ 256 字符（防日志注入 / UI 伪造）。

**明确不修**：孤立代理 `\ud800`（RFC 语法允许、两端一致、不参与运行）、
ZIP 条目 symlink 外部属性（App `ZipEntry` 不暴露 Unix 模式位，且 `install` 用
`FileOutputStream` 写出的是目标文本、不会真的建链）、额外陌生字段（规范未禁止）。

## 9. 导入与释放流程（App 侧，v27）

```
/sdcard/Download/*.frp
   → [扫描列出] → [用户点选]
   → [install：只 new ZipFile(pkg) 一次，校验与落盘共用同一句柄（v23 修 TOCTOU）]
        · 旧实现 verify(pkg) 打开+关闭一次，落盘时再打开一次，中途文件被替换
          就会出现「校验合法包、落盘恶意包」；v23 改为单次打开
        · v24：install / release 均为 synchronized 静态方法，串行化共享的
          .staging / active_pkg.tmp / .bak；并发 80 轮实测由「0 轮双成功」变为 80/80
   → [解到 .staging → active_pkg.tmp → 备份旧 active_pkg → 原子替换]
        · 任一步失败立即返回，原 active_pkg 保持不变
        · 只有确认备份存在时才回滚，绝不无条件 rm -rf(active)
   → [release] active_pkg/payload/* → /sdcard/Download/ksu_fne/   ← App 只做这一步
   → [用户手动] adb / 文件管理器把中转目录 10 项搬进 /data/local/tmp/ksu_fne/ 并 chmod
   → [执行] sh /data/local/tmp/ksu_fne/fne_local.sh（adb / Shizuku / root）
```

- **App 不代搬 tmp**：App 是 `untrusted_app` uid，`rm -rf / cp / chmod` 到 `/data/local/tmp/ksu_fne` 几乎必然 `Permission denied`；更糟的是「曾以 root 跑过 App」时 tmp 属主可能变成 app，那条 `rm -rf` 会把用户手工布置的物料清掉。v21 起 App 只做**只读** `ls -l` 探测，绝不改动 tmp，也不把「写 sdcard 成功」显示成「tmp 已就位」。
- **中转目录** `/sdcard/Download/ksu_fne/`；**最终目录** `/data/local/tmp/ksu_fne/`（e / sh / chain 三处硬编码）。
- `/sdcard` 通常 `noexec`，e/ko 等执行体必须在 tmp 目录运行，sdcard 只作中转。
- 搬运命令可用 App 的「📋 复制搬运命令」按钮获取（**v22 起真正显式列出 10 个源文件名**，由 `ROLES` 派生，不再用 `cp /sdcard/.../*` 通配符）。用通配符会把中转目录里上一次释放的残留、或用户自己放的文件一起搬进 tmp，破坏整包配套；现在残留只提示、不删除，也绝不会被搬走。
- 首次释放完成后不再做 md5/尺寸校验。
- 释放逐项独立 `try/catch`：某一项失败不中断后续，日志如实反映每一项结果；`dest` 含子目录时会建父目录（但 v22 的规则已在 `verify` 阶段拒绝这类 dest）。
- 落盘循环与 `read()` 一样用 `!= -1` 判流结束：`InflaterInputStream` 可能返回 0，用 `> 0` 会提前结束写入，落盘出被截断的物料而校验阶段读到完整数据（v24 修正）。**v25：落盘循环边写边累计真实字节数，超 `MAX_ENTRY_SIZE` 抛异常触发回滚**，即使 ZIP 头声明 size 被伪造也写不进超限数据（第五轮 H6 落地面）。
- `sh -n` 先启动 stdout/stderr 排空线程再写 stdin（防 stderr 缓冲满时写 stdin 死锁），10 秒超时 fail-closed；`shSyntaxOk` 与 `verifyZip` 都兜 `Throwable`。
- 授权状态无法确认时（部分 ROM 的 `isExternalStorageManager()` 抛异常）按**未授权**处理，宁可提示用户去系统设置页，也不拿 `canRead()` 误判为已授权。
- **权限**：Android 11+ 需用户手动开启「所有文件访问权限」，App 有「⚙ 授权文件访问」按钮直达系统设置页；未授权时 `scan()` 扫不到外部 `.frp`，状态栏会红字提示。

## 11. 校验器完整性与威胁模型（v26 修订）

v1 的 `.frp` **没有数字签名**，`manifest.json` 可被改写。校验器的目的是：

- **防误配**：只换 e 不换 sh、换内核不换符号表、`workdir` 改错等；
- **防损坏**：传输截断、缺项、ZIP CRC 错；
- **防散件导入**：不提供任何单文件入口，只能整包导入。

**不防**：攻击者同时改 manifest 与 payload 并让二者自洽（例如替换 `e` 后同步改 `size` / `sha256` / `e_size`）。若分发链路需要防篡改，应在包外对 `.frp` 做签名（minisign / GPG detached sig 等），由导入方在 `verify` 前先验签 —— v1 格式本身不提供该能力。
